# decisions_log.md — архитектурные решения

**Сфера:** решения уровня архитектуры, стека и скоупа. Не журнал задач и не changelog.
**Обновлено:** 2026-09-03.

Формат: решение — почему отвергнута альтернатива. Запись пересматривается через 3 месяца
или при наступлении условия в колонке «Пересмотр». Устаревшие записи удаляются, а не архивируются.

## Активные решения

| Дата | Решение | Почему не альтернатива | Пересмотр |
|---|---|---|---|
| 2026-09-03 | Скоуп MVP — два слоя: скрининг (V4-Flash) и аудит (V4-Pro). Слоёв 0 и 3 нет | Четырёхслойная схема разводила усилия на оркестрацию, пока ядро (NL → релевантные репо) оставалось нераскрытым. Каскад из двух слоёв даёт всю экономию токенов; третий слой добавляет цену и задержку без замеренной пользы | после замера доли неверных вердиктов на golden-set |
| 2026-09-03 | Генерация 5–10 GitHub-запросов из интента — отдельный документированный компонент (`QUERIES.md`) | Один запрос к нессемантическому полнотекстовому поиску пропускает проекты, чей README сформулирован иначе. Это главный источник потерь, и он не лечится ниже по конвейеру: Слой 1 и Слой 2 умеют только отсеивать | после диагностики на 20–30 реальных запросах |
| 2026-09-03 | Строки запросов собирает детерминированный код, модель даёт только интент и синонимы | Модель, пишущая строку запроса целиком, ломает воспроизводимость и регулярно порождает невалидный синтаксис квалификаторов | — |
| 2026-09-03 | Слияние выдач через RRF (k=60) + метаданный приор, веса 0,70/0,30 | Скоры `best-match` и `stars` несопоставимы между собой; калибровать их не на чем. RRF работает с рангами и не требует калибровки | при изменении весов — обязательный замер recall@5 до/после |
| 2026-09-03 | Кэш на уровне репозитория: `repo_id + head_sha` → `AuditResult`. Инвалидация по смене SHA, TTL по времени нет | Кэш по хешу NL-запроса даёт околонулевой hit-rate: запросы не совпадают побайтово. Один репозиторий, наоборот, попадает в выдачу многих разных запросов. TTL по времени либо отдаёт устаревшее, либо жжёт токены на неизменившемся коде | — |
| 2026-09-03 | Работа только через GitHub API. Ни клонирования, ни запуска чужого кода | Запуск произвольного репозитория — исполнение недоверенного кода, причём уже на стадии установки зависимостей. Одного Docker для изоляции недостаточно (нужны no-network, read-only fs, drop caps, лимиты pids). При этом в MVP большинство репозиториев просто не соберётся — цена высокая, отдача близка к нулю | при диагнозе «болит аудит» из-за нехватки сведений о поведении |
| 2026-09-03 | Лицензия — атрибут отчёта, а не фильтр поиска | Фильтр `license:` на входе выбрасывает лучшие проекты в нишах, где сильные решения под GPL. Лицензия влияет на вердикт (`code_reuse_allowed`), но не на попадание в выдачу | — |
| 2026-09-03 | Разделение контекстов: аудит читает код и отдаёт только структурированные факты; генерация кода исходников не видит. Плюс автодетектор фрагментов >120 символов | Идеи и архитектура авторским правом не охраняются, но один общий контекст LLM, который сначала читает GPL-код, а потом пишет свой, оставляет риск дословной регургитации. Разделение — техническая реализация clean-room, а не декларация | — |
| 2026-09-03 | Метрика качества — recall@5 на golden-set из 20–30 задач, цель ≥ 60% | «Точность ≥ 80% на пилоте из 5 задач» неизмерима: пять задач дают шаг 20%. Сравнение экономии токенов с «50 репо через одну большую модель» — сравнение с тем, чего никто не делает; корректная база — тот же конвейер без каскада | после первого замера |
| 2026-09-03 | Модель Слоя 2 — `deepseek-v4-pro`; `qwen3.8-max` только как fallback при 5xx | V4-Pro дешевле при том же контексте 1M: 0,66/1,98 off-peak против 2,00/6,00 у Qwen. Держать обе как равноправные значило иметь непредсказуемую стоимость запуска | ежемесячная сверка прайса |
| 2026-09-03 | Синхронный режим по умолчанию; `--off-peak` — явный опт-ин с отдельным SLA (≤ 12 ч против ≤ 5 мин) | Откладывание по умолчанию противоречит требованию «полный цикл < 5 минут». Это два разных режима с разными обещаниями, а не один компромисс | — |
| 2026-09-03 | Автономно агенту разрешены только запись/инвалидация кэша, повтор после rate-limit и дозапись provenance | Автоправка промптов и весов на потоке в 1–5 пользователей меняет систему быстрее, чем накапливаются данные, чтобы отличить улучшение от шума. Ожидаемая ценность отрицательна | ≥ 500 прогонов и ≥ 5 регулярных пользователей |
| 2026-09-03 | `README.md` (вход для человека) и `CHECKLIST.md` (гейт PR) добавлены в набор документации. Числового правила «строго N файлов» нет; действует: одна сфера на файл, ≤ 200 строк (кроме `SCHEMAS.md`), новый файл только вместе с записью в этом логе. Актуальный состав — в таблице `CLAUDE.md` | Решение пользователя. `README` закрывает сценарий «пришёл человек, а не агент»: `CLAUDE.md` для этого не годится, он контракт с агентом. `CHECKLIST` фиксирует то, чего не видит автоматика: замер recall@5 при правке ранжирования, согласованность чисел между файлами, отсутствие клонирования в diff. Дублирования с pre-commit и Action нет — эти гейты вынесены в отдельный раздел «вручную не дублировать» | — |
| 2026-09-03 | Добавлен `PROGRESS.md` — точка возобновления работы. Всего 9 файлов документации | Сессия с агентом обрывается и начинается заново; `git log` говорит, что сделано, но не говорит, что дальше и какие пункты приёмки остались незакрытыми. Держать это в памяти агента отвергнуто: память переживает не всё и не видна человеку, а прогресс должен быть в репозитории рядом с кодом и уезжать на GitHub вместе с ним | — |
| 2026-09-03 | Промпты хранятся файлами `src/scout/prompts/{intent,l1,l2}/v{N}.md`, версия = имя файла, bump = новый файл + правка `PROMPT_VERSIONS` | Поле `prompt_version` в схемах ссылалось в пустоту: место хранения и порядок версионирования нигде не были заданы, из-за чего запрет 7 («не менять промпты автоматически») был неисполним — нечего было проверять на diff. Правка существующего файла вместо создания нового отвергнута: она задним числом ломает воспроизводимость прошлых прогонов | — |
| 2026-09-03 | Семейство `topic` сортируется по `stars`, а не по `best-match` | Правило сортировки и пример в `QUERIES.md` расходились. Выбран `stars`: в запросе из одних квалификаторов `topic:` нет свободного текста, `best-match` не с чем сопоставлять, порядок выдачи произволен и нестабилен между вызовами | — |

## Отменённые решения

| Дата | Что отменено | Причина |
|---|---|---|
| 2026-09-03 | «Слой 0 — Радар»: ежедневное сканирование трендов GitHub, Hacker News, Reddit, RSS | Смешивал два продукта: push-обнаружение новизны и pull-поиск под конкретную задачу. В запросе «нужен парсер PDF-таблиц» тренды последней недели бесполезны. Плюс скрытая стоимость: GitHub API не отдаёт историю звёзд, «звёздная скорость» требует своей БД снапшотов и начинает работать через месяцы после старта |
| 2026-09-03 | Модуль самоулучшения (§2.6 старого ТЗ) | См. решение об автономных действиях. Дополнительно снимало противоречие: «автономный режим применяет изменения» против запрета менять промпты без ведома пользователя |
| 2026-09-03 | Telegram-бот и Slack-интеграция | Асинхронный канал доставки нужен только асинхронному режиму. Пока `--off-peak` — опция, CLI достаточно |
| 2026-09-03 | Тестовый запуск репозиториев в Docker | См. решение о работе только через API |
| 2026-09-03 | Граф зависимостей и генерация UML | Без исходников строятся только по манифестам и дают немногим больше, чем список зависимостей, который уже есть в `AuditResult` |
| 2026-09-03 | «Мониторинг и обновление моделей» как подсистема с бенчмарками | Фактический объём работы — прочитать ченджлог DeepSeek и Qwen раз в месяц и поправить одну таблицу в `ARCHITECTURE.md` |
| 2026-09-03 | Роадмап на 6 месяцев (MVP 1–2 мес., v1.0 +2 мес., v1.5 +1 мес., v2.0 +2 мес.) | Оценки были перевёрнуты: скрининг с кэшем и CLI — это недели, а не два месяца, тогда как «граф зависимостей + бизнес-сущности + UML + Docker-запуск» — четыре разных проекта, а не один этап на два месяца. Заменён планом на 3 недели с гейтом на данных |
| 2026-09-03 | Запрет «peak-часы 08:00–20:00 UTC» из старого CLAUDE.md | Фактически неверно. Реальные peak-часы DeepSeek: 01:00–04:00 и 06:00–10:00 UTC. Старое ТЗ (§3.3) указывало окна верно, а CLAUDE.md — нет, и агент читал именно его |
| 2026-09-03 | Строка токеномики «Слой 3: V4-Pro или Qwen 3.8 Max, 2,00 / 6,00» | Смешивала цены двух моделей в одной ячейке: 2,00/6,00 — прайс Qwen, у V4-Pro 0,66/1,98 off-peak и 1,32/3,96 peak. Расчёт стоимости на её основе был неверен. Слой 3 отменён, цены разнесены по строкам |
| 2026-09-03 | Формулировка «Двухслойная + опциональная верификация» при четырёх слоях в архитектуре | Нумерация разошлась между документами. Введена единственная сквозная: Слой 1 — скрининг, Слой 2 — аудит |
| 2026-09-03 | Mermaid-диаграмма старого ARCHITECTURE.md | Невалидный синтаксис (цепочки стрелок, `/` в идентификаторах узлов) — не рендерилась. Заменена рабочей |
| 2026-09-03 | «Документация — 6 файлов, у каждого одна сфера» | Уточнено: пользователь утвердил добавление `README.md` и `CHECKLIST.md`. Состав набора — в таблице `CLAUDE.md`, см. активную запись выше |
