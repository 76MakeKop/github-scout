# QUERIES.md — генерация поисковых запросов и переранжирование

**Сфера:** превращение NL-задачи в набор GitHub-запросов и сведение выдач в один список.
**Обновлено:** 2026-09-03.

Это ядро системы. Каскад моделей ничего не спасёт, если на вход придёт мусор:
Слой 1 и Слой 2 умеют только отсеивать, найти пропущенное они не могут.

## Ограничения GitHub Search API

Из них следует вся конструкция ниже.

- Поиск **не семантический** — это полнотекстовое совпадение по имени, описанию,
  README и топикам. Синонимы не раскрываются сами.
- **1000 результатов** максимум на запрос, 100 на страницу.
- **30 запросов в минуту** для аутентифицированного клиента.
- Релевантность `best-match` непрозрачна и нестабильна между вызовами.

Вывод: один запрос недостаточен и ненадёжен. Нужно 5–10 разных запросов,
по одной странице с каждого, и своё переранжирование поверх.

## Шаг 1. Интент (V4-Flash, 1 вызов)

NL-запрос → `Intent` (схема в `SCHEMAS.md` §2). Модель извлекает:
задачу одним предложением, домен, язык, обязательные и исключаемые свойства,
**3–10 англоязычных синонимов** и **до 8 гипотез об именах известных библиотек**.

Синонимы и гипотезы имён — самая ценная часть. Пользователь пишет «парсер PDF-таблиц»,
а в README целевого проекта написано `table extraction from PDF documents`.
Разрыв закрывает именно этот шаг.

`temperature = 0`, версия промпта фиксируется в `prompt_version`.

## Шаг 2. Семь семейств запросов (детерминированный код)

Код собирает запросы из `Intent` по шаблонам. Модель строки запросов не пишет —
иначе теряются воспроизводимость и валидность синтаксиса квалификаторов.

| Семейство | Шаблон | Зачем |
|---|---|---|
| `exact` | `{synonyms[0]} language:{lang} archived:false` | прямое попадание |
| `synonym` | `{synonyms[1]} language:{lang} archived:false` | другая формулировка той же задачи |
| `topic` | `topic:{domain[0]} topic:{domain[1]} archived:false` | кураторские топики, не текст |
| `library` | `{known_libraries} in:name,description` | гипотезы имён библиотек, OR-список |
| `readme` | `"{synonyms[2]}" in:readme language:{lang} archived:false` | точная фраза внутри README |
| `broad` | `{core_noun} language:{lang} stars:>50 archived:false` | широкий невод против переспецификации |
| `recent` | `{synonyms[0]} language:{lang} pushed:>{today-540d} archived:false` | живые проекты, сортировка по `updated` |

`core_noun` — поля с таким именем в `Intent` нет, его выводит код: первые два значимых
слова из `synonyms[0]`, служебные отброшены. Меньше слов — шире выдача, а это и есть
задача семейства. Переформулировать синоним код не пытается: морфологию ему взять неоткуда.

Правила сборки:

- `language:` подставляется, только если `Intent.languages` непуст. Иначе квалификатор опускается.
  Берётся **первый** язык из списка: квалификаторы GitHub объединяются по И, и два `language:`
  дали бы гарантированно пустую выдачу.
- `archived:false` — во всех семействах, кроме `library`.
- **`license:` не используется никогда.** Лицензия — атрибут отчёта, а не фильтр
  (`CLAUDE.md`, запрет 4). Отсекать GPL на поиске значит выбрасывать лучшее.
- `stars:` — только в `broad`. В остальных семействах порога нет: узкая ниша
  может не иметь ни одного проекта со звёздами.
- Итог: 5–10 запросов, и **всегда не меньше 5** — `SCHEMAS.md` §3 задаёт `minItems: 5`.
  Если из бедного интента (нет синонимов, нет топиков) собралось меньше, генератор
  добирает широкий невод без `language:` и без `stars:`; если и это не помогло —
  `QueryGenerationError`, скан прекращается. Больше 10 запрещено лимитом
  (`CLAUDE.md`, запрет 5).

**Сортировка.** `topic`, `library` и `broad` → `sort=stars`. `recent` → `sort=updated`.
Остальные (`exact`, `synonym`, `readme`) → `best-match`. Разные сортировки дают разные
срезы, и это именно то, что потом склеивает RRF.

`topic` сортируется по звёздам, а не по релевантности: в запросе из одних квалификаторов
`topic:` нет свободного текста, и `best-match` не с чем сопоставлять — порядок выдачи
получается произвольным и нестабильным между вызовами, что ломает воспроизводимость.

### Пример: «нужен парсер PDF-таблиц на Python»

Дата сборки — 2026-09-03; от неё считается окно `pushed:` в `q7`.

```
q1 exact    pdf table extraction language:python archived:false                     best-match 30
q2 synonym  extract tables from pdf language:python archived:false                  best-match 30
q3 topic    topic:pdf topic:table-extraction archived:false                         stars      30
q4 library  camelot OR tabula OR pdfplumber OR unstructured in:name,description     stars      30
q5 readme   "pdf table parser" in:readme language:python archived:false             best-match 30
q6 broad    pdf table language:python stars:>50 archived:false                      stars      30
q7 recent   pdf table extraction language:python pushed:>2025-03-12 archived:false  updated    30
```

Блок не написан от руки — он снят с вывода генератора, и тест
`test_queries_md_example_block_matches_generator` читает его прямо отсюда и сверяет
с кодом. Разойтись молча, как это дважды случилось раньше, пример больше не может.

7 запросов × 1 страница = 7 HTTP-вызовов, троттлинг 2 с между ними ≈ 14 с.
До 210 результатов до дедупа.

## Шаг 3. Дедупликация

1. Ключ — `repo_id` (не `full_name`: репозиторий может быть переименован).
2. При склейке дублей сохраняется **список** `found_by` — все запросы, которые его нашли.
   Это сигнал: репозиторий, найденный четырьмя разными формулировками, почти наверняка релевантен.
3. Форки схлопываются к родителю: если в выдаче есть и `A/x`, и её форк `B/x`
   (`is_fork: true`, тот же `parent.id`), остаётся родитель. Форк без родителя в выдаче — остаётся.
4. Жёсткое отсечение до ранжирования: `archived: true`, отсутствие языка **и** описания
   **и** топиков, `size == 0`.

## Шаг 4. Переранжирование: RRF + метаданные

**Reciprocal Rank Fusion** — стандартный способ слить несколько ранжированных списков
без калибровки их скоров между собой. Ровно то, что нужно: сравнивать `best-match` из
q1 со `stars` из q6 напрямую нельзя, а их ранги — можно.

```
rrf(r) = Σ  1 / (k + rank_q(r)),   k = 60,  по всем q, где r встретился
```

`k = 60` — общепринятое значение; оно гасит вклад разницы между 1-м и 2-м местом
и не даёт одному запросу продавить свой топ.

Нормализация: `rrf_norm(r) = rrf(r) / max_r rrf(r)`.

**Метаданный приор** — против свежесозданных пустышек, которые хорошо совпадают текстом:

```
prior(r) = 0.40 * min(log10(stars + 1) / 4, 1)
         + 0.30 * clamp(1 - days_since_push / 540, 0, 1)
         + 0.15 * (license_spdx is not None)
         + 0.15 * (not is_fork)
```

**Итог:**

```
score(r) = 0.70 * rrf_norm(r) + 0.30 * prior(r)
```

Сортировка по `(score DESC, repo_id ASC)` — второй ключ гарантирует идемпотентность
при равных скорах. Топ-50 идёт на Слой 1.

Веса `0.70 / 0.30` и коэффициенты приора — гиперпараметры. Менять их разрешено только
после прогона golden-set (`ROADMAP.md` → «Оценка качества»), с записью до/после
recall@5 в `decisions_log.md`. Автоматическая подстройка запрещена (`CLAUDE.md`, запрет 7).

## Шаг 5. Вырожденные случаи

| Ситуация | Действие |
|---|---|
| Суммарно < 10 уникальных кандидатов | добавить прогон `broad` без `language:` и без `stars:` |
| Суммарно 0 кандидатов | отчёт с рекомендацией BUILD, в `queries_used` — все 7 строк |
| Один запрос вернул 0 | норма, не ошибка; RRF работает по остальным |
| Все кандидаты — форки одного проекта | схлопнуть к родителю, добрать из `broad` |
| `Intent.languages` пуст | все шаблоны без `language:`, `broad` получает `stars:>100` |
| 403/429 от Search API | backoff по `ARCHITECTURE.md`; при исчерпании попыток — ранжировать по тому, что успели собрать, и пометить отчёт `partial: true` |

## Что здесь заведомо неидеально

Известные слабости MVP — фиксируются, чтобы их проверяли на golden-set, а не
чтобы чинить заранее:

- Полнотекстовый поиск пропустит проект, чей README написан в других терминах,
  чем все 10 синонимов. Частичное лекарство — семейство `library`.
- `prior` штрафует новые качественные проекты (мало звёзд, мало истории).
- Русскоязычная формулировка задачи целиком зависит от качества перевода на шаге 1.

Если после 20–30 реальных запросов recall@5 упирается именно в эти пункты —
следующий шаг развития проекта здесь, а не в новых слоях.
